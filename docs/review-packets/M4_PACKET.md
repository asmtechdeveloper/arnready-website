## 1. Scope

M4 gives the website its own `progressService`, writing progress, session and
mistakes documents **byte-identical** to the app's
`progressService.recordExamSession` / `recordPracticeSession` /
`recordFlashcardSession`, plus the `mistakesService.updateMistakesFromRun` hook
those write sites fire.

The parity claim is not a promise in a comment — it is mechanical. A fixture
file of `(session input → expected document)` pairs is **generated by running
the app's real services**, and lives byte-identical in both repos. The app repo
asserts its services still produce those documents; this repo asserts the port
produces the same ones. Either side drifting fails the other's suite.

Because `recordExamSession` computes its next document from the previous one,
the port necessarily includes the app's read/normalize layer as well
(`docToBlob`, `buildBlob`, `normalizeSampleScope`, `scopeBlobFrom*Fields`,
`classifyLegacyTotal`). All of it is ported, none of it re-derived.

## 3. The fixtures (review protocol §2.6 and §4 M4)

### Provenance — generated FROM the app service, not hand-written

`../ARNReady-App/__tests__/progressParityFixtures.test.js` imports the **real**
`services/progressService.js` and `services/mistakesService.js` and runs them.
Only React Native infrastructure is mocked — `@react-native-firebase/firestore`,
`@react-native-firebase/auth`, AsyncStorage. **No service logic is stubbed**;
notably `mistakesService` is *not* mocked, so its real deck behaviour is
captured. The Firestore double is a recorder: it captures document paths, merge
flags and payloads, and serves per-case prior state.

Regenerate with:
```
ARNREADY_WRITE_PARITY_FIXTURES=1 npx jest progressParityFixtures
```

This is materially stronger than M2's golden fixture, which established
provenance by citation rather than by execution.

### Sentinel encoding

Firestore sentinels have no JSON form. Both repos' doubles encode them
identically as `{ __sentinel: 'serverTimestamp' }` and
`{ __sentinel: 'increment', by: n }`. This is what makes the review protocol's
timestamp-semantics check enforceable: a client `Date` where the app writes
`serverTimestamp()` cannot compare equal. Demonstrated in §3.2 below.

## 5. The one modified pre-existing test (review protocol §3.9)

`test/isPaidDiscipline.test.ts` is modified. Flagging it prominently, because
"any pre-existing test modified to pass = investigate" is exactly the right
instinct here. This section describes its **final, post-M4-r state**; the
intermediate state at `a148a57` was more permissive and is what M4-B1 caught.

M3 asserted that **no** `src/` module imports or calls any Firestore write API,
and recorded in that file why: *"user document creation is M4's, and it will add
these imports deliberately, in one reviewed service."* M4 writes progress,
sessions and mistakes, so that assertion had to change. M3's note also expected
M4 to create the user document — M4-B1 established it cannot (§6.3).

It was **narrowed, not relaxed**:

- Every write API is still banned across all of `src/`, with exactly one
  allowlisted file (`WRITE_SITE = 'lib/progressBackend.ts'`). The guarantee moves
  from "nothing writes" to "exactly one reviewed module writes" — the strongest
  form available once the product must write at all.
- The API-call scan gained a negative lookbehind so `backend.increment(...)` (a
  call on the injected seam) is not confused with the SDK's `increment(...)`. A
  bare `increment(` in a service file still fails.
- `users` access is split: `lib/entitlementStore.ts` may **read** (M3's
  listener); nothing may write the root document.
- The `isPaid` reader allowlist is **unchanged from M3** —
  `entitlementStore`, `nudgeGates`, `AppShell`. M4-r restored it after M4-B1;
  the write site does not appear on it.
- **Two assertions added**, both strictly tightening:
  - the write site never names `isPaid` **at all** (not "only writes it as
    false" — the field is absent from the module entirely);
  - no `src/` module writes the `users` root document or runs a transaction on
    it.

Net: 19 assertions → 21, and the two additions are absence proofs rather than
constraints on a permitted write. No assertion was deleted or weakened relative
to M3.

## 6. Deviations from the manual

Three, all authorized or forced, none silent.

**6.1 — No local cache (Anusha, 2026-07-19).** The app mirrors every write into
a device-local AsyncStorage blob (`examResults_{n}`) and falls back to it when
Firestore is unreachable. The web port is Firestore-only. The manual's parity
requirement is over Firestore **documents**; the cache is React Native device
state with no web equivalent, and caching user progress in browser storage would
cut against the entitlement-caching discipline M3 established (and which
`isPaidDiscipline.test.ts` still pins). Consequence: `getChapterProgress`
returns `null` rather than stale local data when Firestore cannot be reached —
strictly the more conservative behaviour. `normalizeCachedBlob` and
`readCache`/`writeCache` are therefore not ported.

**6.2 — `recordPracticeSession` omits the opening read.** Follows directly from
6.1. The app opens that function with `getChapterProgress` solely to fold the
result into the cache blob. With no cache, the read has no consumer; it is
omitted rather than performed and discarded. **This cannot change any
document**: the practice aggregate is a field increment (never derived from
prior state) and the session log does not consult `prev`. `recordExamSession`
still reads, because its documents *and* its return value genuinely depend on
`prev`. Documented at the function in a `PORT NOTE`.

**6.3 — `ensureUserDocument` is REMOVED (M4-r, Codex M4-B1).** M4 originally
included a ported `ensureUserDocument`, per Anusha's 2026-07-19 decision that M4
owns the user-document write shape. Codex rejected it as a manual §0.9
violation, and the finding is correct: the deployed rule
`allow create: … request.resource.data.isPaid == false` means a client-side
create MUST send `isPaid`, while §0.9 says no client code path may write that
field. Both cannot hold. The packet previously argued the rule *justified* the
write — that argument was wrong. A rule requiring the field is evidence that
client-side creation of that document is unavailable to the web, not permission
to do it.

Removed entirely in M4-r. `src/lib/progressBackend.ts` now contains no
`runTransaction`, no `users/{uid}` root write, and **no occurrence of the string
`isPaid` at all**; `test/isPaidDiscipline.test.ts` is restored to its M3
allowlist and gains two assertions pinning that absence.

**Nothing in M4 needed it**, which is why this is a scope reduction rather than
a redesign:
- the deployed `users/{uid}/{document=**}` rule grants every progress, session
  and mistakes write **without** the parent document existing — confirmed by the
  live session in §4, which wrote all of them successfully;
- free question reads are gated on `isFree == true`, which does not consult the
  user document either.

**What this leaves open, for M5 to raise rather than assume.** The user document
IS consulted by the deployed `questions` rule for PAID full-bank reads
(`exists(users/{uid}) && isPaid == true`). For a paying user that document is
created server-side by the purchase chain, so the common path is covered. If M5
or M6 finds a surface that genuinely requires the web to create it, that is a
canon question for Anusha — either an explicit §0.9 amendment or a Cloud
Function in the app repo's `functions/` (itself a §0.10 stop condition). It must
not be re-introduced client-side on an executor's judgement.

### Not a deviation, but worth stating

The port deliberately reproduces the app's **lack** of type validation on stored
fields. `src/lib/progressService.ts` reads via a `field<T>()` helper that mirrors
the app's bare `?? fallback` — only `null`/`undefined` fall through. An earlier
draft used a `typeof` guard; that was **removed**, because it would diverge from
the app on a malformed document (a stored `"5"` passes through in the app but
would have become the fallback here). Unreachable with well-formed data, but
"ported, never re-derived" admits no exception for improvements.

## 7. Pre-commit adversarial review and its fixes

The port was reviewed function-by-function against the three app source files,
first by the orchestrator and then by an independent read-only subagent briefed
to find inputs producing different output in the two implementations. The two
approved deviations (§6.1, §6.2) were declared to it up front so it would not
re-report them. **Six findings; all six are fixed in this commit.** They are
recorded here because they are exactly what Codex should re-derive
independently — this section is a disclosure, not a claim of clearance.

### Fixed before the review returned

**P1 — read helper was more defensive than the app.** The first draft read
stored fields through a `typeof v === 'number'` guard where the app uses a bare
`?? fallback`. On a document holding `sampleLastTotal: "20"`, the app builds a
blob with `lastTotal: "20"` (and normalizes to a 70% best pair) while the draft
built `lastTotal: 0`. This reaches a **write**, not just a read:
`recordExamSession` re-persists `prev.sample` through `sampleFields(...)` on a
FULL attempt and derives `previousExamScore/Total` from `prevScope`. Replaced
with a `field<T>()` helper carrying the app's exact `??` semantics. (The
subagent independently found this as its F5, against the pre-fix file.)

### Found by the subagent, fixed after

All four concern `ensureUserDocument`, which the parity fixtures stub — so, as
the subagent correctly observed, **none of these was covered by any gate**. That
gap is closed by the new `test/ensureUserDocument.test.ts` (11 tests, every
branch).

> **Superseded by M4-r.** P2–P5 all concern `ensureUserDocument`, which Codex
> M4-B1 has since removed from the milestone entirely (§6.3). They are retained
> here unedited because they are the record of what the pre-commit review found,
> and because P2's reasoning error is instructive: I corrected a deliberate
> narrowing *towards* the app, when the correct move was to remove the function
> because the website canon forbids it regardless of what the app does. The
> subagent measured the port against the app; neither of us measured it against
> §0.9. Codex did.

**P2 — the existing-document merge branch was dropped.** The app writes
whitelisted profile fields with `{ merge: true }` when the document already
exists; the port made that branch an unconditional no-op. This was originally a
*deliberate* narrowing, declared in an earlier draft of §6.3 on the reasoning
that fewer writes to `users/{uid}` is safer. **That reasoning was wrong for this
milestone**: parity is the requirement, the manual's forbidden list names "any
deviation in … mistakes-hook behavior" and the protocol calls a web-only
improvement a BLOCKER, and porting the branch faithfully costs nothing because
the whitelist makes it a no-op when no profile is supplied. Now ported verbatim.

**P3 — `newsletterOptIn` was structurally unreachable.** The app whitelists two
client-owned fields and spreads them into the creation payload; the port's
signature admitted only one, so a web-created account would carry no
`newsletterOptIn` field at all where the app writes `true`. Both fields are now
whitelisted, with the app's `typeof` guards.

**P4 — `?? ''` fallbacks were lost (the sharpest of the six).** The app writes
`displayName: … ?? user.displayName ?? ''` and `email: user.email ?? ''`.
Firebase Auth types both as `string | null`, so a **Google account with no
display name** produced `displayName: ""` in the app and `displayName: null` on
the web — two different Firestore values for an identical sign-in. The
TypeScript `string` annotation gave no runtime protection. Fallbacks now applied
inside the function, as in the app, and pinned by test.

**P5 — the target user was read from ambient auth state.** The app takes an
explicit `user` argument; the port re-read `getAuthClient()?.currentUser?.uid`
inside the transaction. During a sign-in/sign-out flap that resolves to a
different account — or to nothing, silently creating no document. Now passed
explicitly, with a test asserting the write follows the argument and not the
ambient uid.

**P6 — `writeSessionLog` was not exported.** It is public in the app, consumed
by `mockService.js` and `baselineService.js`. Privatising it would have left
M6's mock port unable to reach the single session-log write site — pushing it to
restate the session shape, the exact duplication `singleWriteSite.test.ts`
exists to prevent. Now exported, with no M4 caller.

### Checked and found faithful

`buildBlob` (guidance merge, all eight defaults, the attempts sum);
`scopeBlobFrom*Fields` (field names, fallback chains, percentage derivations);
`normalizeSampleScope` (line-for-line, including the NaN-safe `!(lastTotal > 0)`
guard and the strict `lastPercentage > bestPct` comparison); `classifyLegacyTotal`;
`docToBlob` (branch order and the early return); `writeSessionLog` (payload
field-for-field, including the `detail` mapping and all four defaults);
`recordExamSession` (scope validation, `denom`, the `prevBestPct`/`isNewBest`
logic including the `bestTotal === 0` case, both aggregate branches with
`sampleFields` spread last on FULL, and the write dispatch order);
`recordPracticeSession` and `recordFlashcardSession`; and `updateMistakesFromRun`
(guards, streak advance, retire threshold, push order, commit-only-if-non-empty).

Two specifics worth recording, both verified: `Array.prototype.filter` passes the
original-array index, so `wrong` pairs each answer with its own question; and
`prevScope` is provably non-null on the branch reading `prevScope.bestScore`,
because a null `prevScope` forces `prevBestPct` null, which forces `isNewBest`
true.
